This release introduces the extensions framework: a small set of typed integration seams that let external software supply behavior acp-stack deliberately does not implement. An extension is declared as data in `[extensions.<name>]` and fulfilled by whatever external software satisfies the contract — there is no dynamic route registration, no in-process plugin loading, and nothing extension-specific compiled into acp-stack.

## Extensions framework

- `[extensions.<name>]` declares typed instances; the table key is the operator-chosen instance name (lowercase alphanumeric with interior hyphens, at most 64 bytes) because it becomes an API path segment and a diagnostics label. Fields are scoped to the declared type, so a field that would enforce nothing for that type is rejected at config load rather than silently ignored.
- Declarations have no CLI surface — imported or directly edited TOML is the only way to configure them. `acps extensions status` reports the declared instances read-only.
- Both contracts are explicitly versioned: the network-provider environment contract advertises `ACPS_SANDBOX_NETWORK_PROTOCOL=1`, and the managed-state request schema is gated on `schema_version = 1`.

## Type `network-provider`

- Replaces `[workspace.sandbox.network]`. Declaring an instance switches every sandboxed spawn — agent harness and each mediated command alike — to a fresh per-spawn network namespace whose policy belongs entirely to the external provider executable. Requires `[workspace.sandbox] mode = "unshare"`, and at most one instance may be declared.
- An empty or omitted `provider` argv means deny-all networking: acp-stack configures nothing, not even loopback.
- `acps workspace sandbox set` refuses, without writing, a mode change that would conflict with a declared network-provider instance.

## Type `managed-state`

- Grants an external orchestrator ownership of one named state namespace through a single fixed admin route, `POST /v1/admin/extensions/{name}/apply`. The only capability today is `provider-credential`: the namespace holds at most one provider credential selection, stored in the encrypted secret store's catalog exactly like an operator-managed credential but marked with the namespace as its provenance source.
- Revision ordering is enforced in the store and persisted atomically with the credential catalog swap: a higher revision applies, an equal revision with identical content is an idempotent no-op, and an equal revision with different content or a lower one is rejected with `409` `extensions.revision_conflict`. `selection` is a required key that may be `null` to clear the namespace; a missing key is a parse error rather than a destructive clear.
- Ownership is store-level provenance, not endpoint behavior. A namespace may create catalog entries or replace its own and nothing else; applying onto an operator-managed or another namespace's credential is `400` `extensions.state_ownership`, and operator credential flows symmetrically refuse to modify externally-owned entries.
- Credential values are validated against the provider's canonical env-var contract and never appear in responses or logs. Every apply records a `server.extension_managed_state_applied` audit event carrying the namespace, outcome, revision, and provider id.
- The declared namespace set is resolved from the config the daemon started with, so a config import that adds a `managed-state` instance answers `404` until the next daemon start.

## Breaking config change

- `[workspace.sandbox.network]` no longer loads. Config containing it fails with a migration error pointing at the replacement: declare `[extensions.<name>]` with `type = "network-provider"` instead. The `provider`, `provider_timeout`, and `provider_stderr` fields carry over unchanged; the old `mode = "isolated"` toggle is now implied by the presence of the declaration.

## Internal

- Oversized runtime modules and test binaries were split into focused siblings under their existing parents. No behavior change; external module paths are unchanged.
