This release adds day-2 Agent Skills management across the API, CLI, and config, on-demand agent update and version-status routes, and hosted-init state streaming with per-category signals. It adds Kilo Code, Kimi Code, and Google Antigravity as supported native agents (and removes Cursor CLI), introduces per-provider endpoint overrides with per-model wire-shape routing for Hermes, expands the provider catalog substantially, makes agent switches resumable and installer progress observable, and adds a per-session agent slash-command surface. It also publishes a machine-readable JSON Schema for the `/v1` API and config, and unifies wire-contract spellings — several of these are breaking changes for API clients, detailed below.

## Breaking changes and migrations

- **Wire spelling `canceled` → `cancelled` (double-l) everywhere.** Command status, permission request status, permission decisions, hosted-init session status, the event kinds `command.cancelled` / `permission.cancelled`, permission-decision reasons (`command-cancelled`, `session-cancelled`), and the `server.reconciled` payload field `permissions_cancelled` all use the new spelling. Migration 024 (`terminal_status_spelling`, sqlite + postgres) rewrites stored rows automatically on state open; historical event payloads and decision reason text are deliberately not rewritten. Clients matching the old strings must update.
- **`POST /v1/agent/switch` request field `agent` renamed to `agent_id`**, and its response `models` is now a list of `{value, display_name?}` objects (same shape as `GET /v1/models`) instead of plain strings. Agent update reports and `agent.update.*` event payloads likewise renamed `agent` → `agent_id`. `ignored_features` entries renamed `target` → `value`, with `feature` pinned to `mcp.server|agent.mode|agent.model`.
- **All native-config error codes gain the `agent.` prefix** (e.g. `agent.native_config_operation_not_found`, `agent.native_config_rollback_conflict`). Framework-generated envelopes are rewrapped as `request.not_found`, `request.method_not_allowed`, and `server.internal_error`.
- **Hosted init (`acps init serve`) replaces the `state` frame with raw `signal` events.** The server-frame vocabulary is now `hello`, `progress`, `signal`, `input_required`, `input_accepted`, `result`, `error`. Each `signal` frame carries one fact (`step_started`, `step_finished`, `category_applicability`, `category_settled`, `category_provisionally_settled`, `category_failed`); the instance no longer derives the nine-category status view — clients fold the stream themselves (a reference fold ships in the test suite). The `state` snapshot in `hello` and `GET /v1/init/sessions/{id}` is replaced by a `signals` replay array with `last_seq`, and on `init.ws_lagged` the server re-sends `hello` so clients can re-fold. Hosted clients consuming `state` frames must migrate.
- **Custom-provider credential deferral is now explicit.** A hosted init run only soft-passes a missing custom-provider api-key ref when the start request declares `defer_provider_credentials: true`; without it the run hard-fails, same as terminal runs. The streamed prompt kind `custom_provider_confirm` is removed.
- **Codex + `openai` now takes `OPENAI_API_KEY` as an ordinary keyed provider**; the Codex-native auth lane is removed. Operators relying on Codex's own login must store a key (`acps agent provider credential add openai` or `acps secrets set OPENAI_API_KEY`). `acps agent switch` to codex reusing `openai` now keeps the inherited `api_key_ref` instead of dropping it.
- **Cursor CLI support is removed**: the `cursor` registry entry, the `CURSOR_API_KEY` managed secret ref, and the `cursor` provider are deleted, so `--agent cursor` is no longer accepted by init, switch, or install. There is no automatic migration for existing cursor configs — operators must `acps agent switch` to a supported agent or declare a custom harness pointing at Cursor's install script.
- **Custom-provider config validation is stricter**: custom-provider ids may not collide with the mapped-provider registry (registry ids are reserved instance-wide; choose e.g. `anthropic-1`), and one custom-provider id must name the same `api_key_ref` across every declaration. Conflicting existing configs now fail validation.
- **Provider key renames**: `zhipuai` no longer shares `ZAI_API_KEY` with `zai` — it takes its own `ZHIPU_API_KEY` and its Claude Code endpoint moved to `https://open.bigmodel.cn/api/anthropic` (keys are not interchangeable with `api.z.ai`). The opencode `arcee` key renamed `ARCEEAI_API_KEY` → `ARCEE_API_KEY`, and opencode `meta` reads `META_MODEL_API_KEY` (Hermes lanes unchanged). Affected operators must re-store the renamed secrets.
- **`acps deps apply --json`** outcome kinds respelled `alreadypresent` → `already_present`, `privilegerequired` → `privilege_required`.

## Agent Skills management

- New day-2 skills API under the active agent: `GET /v1/agent/skills`, `GET /v1/agent/skills/catalog`, and `GET /v1/agent/skills/source?source=<ref>` (session tier, also on the local socket); `POST /v1/agent/skills/add`, `POST /v1/agent/skills/remove`, and `POST /v1/agent/skills/sources/add|remove` (admin tier, serialized with agent switch via the config mutation lock). Sources resolve as a curated-catalog alias, a configured alias, or `github:<owner>[/<repo>]`; new error codes include `agent.skill_not_installed` (404) and `agent.skill_source_not_configured` (404).
- Matching CLI surface: `acps skills list`, `acps skills catalog`, `acps skills add <source> <selector>...`, `acps skills remove <name>`, and `acps skills source get|add|remove`. Mutations require the admin key; reads fall back to the local read-only socket when `[local].session_auth = "keyless"`.
- New config table `[[skills.sources]]` (`alias`, `github`, optional `branch` and `trusted`) for user skill sources. An individually invalid entry is skipped with a warning at startup, never fatal; a `source add`/`remove` write heals previously dropped entries with a per-entry warning.
- Each installed skill now carries a `.acp-stack-managed` marker recording its source. **Migration note**: skills installed by earlier releases have no marker and are treated as user content — `acps skills remove` refuses them (`409 agent.skill_install_target_conflict`); delete them by hand and re-add with `acps skills add`. Agent switch replaces same-named target skills only when managed, reporting hand-placed folders as `kept_unmanaged`.
- All supported agents now share the `~/.agents/skills` install dir (Amp's moved from `~/.config/agents/skills`), so switches never copy skills; Hermes and Claude Code keep their discovery dirs populated via managed symlinks.

## Agent updates and version status

- New routes: `POST /v1/agent/update` (admin) runs the managed update synchronously — the same code path as the auto-update timer — with an optional `{"force": true}` body to reinstall at the same version; a running agent or a concurrent request returns `200` with `skipped: true`, so retries are safe. `GET /v1/agent/update/status` (session) reports per-component `up_to_date`/`stale`/`unknown`/`not_installed` against floating upstream latest, the configured pin, and the auto-update policy; an upstream lookup failure degrades the component to `unknown` rather than failing the request.
- `acps init` gains `--agent-update <on|off>` and `--agent-update-frequency <FREQ>` (hour/day/week units, minimum 1 hour), with a matching interactive prompt for managed registry agents, so auto-update can be declined at init instead of only afterwards. Frequencies now accept hour/day/week units with a 1-hour minimum (stack update frequency stays day/week, minimum 1 day). The hosted init start request mirrors all four fields (`stack_update`, `stack_update_frequency`, `agent_update`, `agent_update_frequency`).
- The `harness_version` pin now constrains managed updates as well as install: a pinned agent updates to its pin rather than latest (GitHub Release harness path only) and reports up-to-date at the pin, while the status route still reports `stale` once upstream moves on.
- Custom (non-registry) agents are cleanly skipped end to end: `acps agent check` and `acps agent update` exit 0 with a skipped report (resolved before any daemon interaction, so `--restart` never restarts for a no-op), `acps agent update set` rejects auto-update flags for them, and the daemon auto-updater records `agent.update.skipped` events instead of erroring each cycle.
- A failed binary swap during `acps update` now surfaces the typed error `stack.update_binary_swap_failed` with rollback-status-aware messages and remediation hints.

## Init and the hosted bootstrap API

- New `acps init --mode <mode-id>` selects the initial session mode, validated against the agent's ACP-advertised modes via the provisional session shared with model discovery; interactive init gains a searchable mode picker for agents that support modes. The hosted start request accepts `mode`, `resume`/`fresh`, and a full custom-agent field group (`custom_agent_id` plus command/args/install/creates), with cross-field anchor rules validated as `400` naming the field.
- Hosted pending-input payloads are now self-describing: each prompt carries a machine-readable `kind` and per-option `index`/`value`/`label`/`hint`, and answers may use a stable `{"value": "<id>"}` in addition to index/label. Post-install MCP prompts now stream to hosted clients when no MCP server was declared up front.
- New typed init error codes: `init.canceled` (now `init.cancelled`, see breaking changes), `init.invalid_param`, `init.provider_write_failed`, `init.model_write_failed`, `init.mode_write_failed`, `init.mcp_write_failed`, `init.skills_install_failed`, `init.secret_store_unavailable`, `init.finalize_failed`, `init.config_reload_failed`, and `init.frame_encode_failed`.
- A hosted client answering the testflight prompt may carry `deferred: true` beside `value: false`, recorded as the new `SkipDeferred` decision ("testflight: deferred (runs after setup)") — the hosting backend will run the testflight itself, distinct from an operator declining. Client frames now ignore unknown fields rather than rejecting them.
- Custom-provider credential handling is tightened across init, apply, and spawn: managed-state credential apply accepts a custom provider only when the running agent config declares it (unknown provider ids are rejected before any revision persists, so an early apply can be retried); a catalog credential now wins over a bare `[agent].env` ref of the same name, so managed rotation takes effect without touching the flat store; and a missing custom-provider key fails agent start with a remediation naming the provider and ref.

## Agents: Kilo Code, Kimi Code, and Google Antigravity added; Cursor removed

- Kilo Code (`kilo acp`, npm `@kilocode/cli`) is a supported native, headless-compatible agent with model and mode selection (`build`/`plan`) and env-var credential setup (`KILO_API_KEY` — distinct from the Hermes provider's `KILOCODE_API_KEY`), verified end-to-end (the previously suspected upstream `session/prompt` hang for headless stdio clients is confirmed fixed). Kilo's default active provider is its own gateway and stalls the ACP session without a credential; to run a provider-native key instead, declare `KILO_PROVIDER` (secret value = the provider id, e.g. `openrouter`) alongside that key. The harness still requires `KILO_API_KEY` present but accepts it empty, so init, `acps config import`, and `acps agent set --model` seed the declaration and an empty placeholder automatically when a recognized provider-native credential is declared.
- Kimi Code (`kimi acp`) is verified end-to-end and now listed as supported. Auth is fully headless through the `KIMI_MODEL_*` launch environment `acp-stack` constructs from the secret store — no interactive OAuth. It gains provider selection between mapped lanes: the Kimi For Coding subscription surface (`kimi-code` and aliases, plus the new global-region `kimi-coding-global`, both on `KIMI_API_KEY`), the pay-as-you-go Moonshot AI platform (`moonshotai` / `moonshotai-cn`, on `MOONSHOT_API_KEY`), and custom Anthropic-/OpenAI-compatible endpoints (`--provider-api chat-completions|anthropic-messages|responses`, mapped onto `KIMI_MODEL_PROVIDER_TYPE`). Init pins a per-lane default model (`kimi-for-coding` on subscription lanes, `kimi-k3` on the platform); a legacy config without `[agent.provider]` still launches on the subscription lane.
- Google Antigravity is a supported native agent via Google's official `antigravity-acp` server from the upstream ACP registry (Linux x86_64/aarch64), verified end-to-end. Headless auth has two parts, both managed by `acps`: `auth.type: "gemini-api-key"` written into `~/.gemini/antigravity-acp/settings.json` and `GEMINI_API_KEY` (a Google AI Studio key) in the launch environment. Model and mode selection follow the server's per-session advertisement — Gemini 3.x model/thinking tiers and the modes `default`/`auto_edit`/`yolo`; `default` raises a permission request on every file edit, so unattended runs should use `auto_edit` or `yolo`, and free-tier keys can stall on the default model (pinning e.g. `gemini-3.5-flash-low` is recommended). The install resolves the archive from the upstream registry index, and re-running the install recipe is the update path via the new registry flag `update.shell_rerun` (agent-update step reports may now carry `method: "shell"`).
- Cline was added mid-cycle (shipped only in nightly v0.1.9.11) and removed again: in ACP mode its only credential is a Cline account key obtained through browser OAuth, with no documented headless provider-key path, so it fails the API-key / no-browser-OAuth support bar. It can still be run as a custom harness (`cline --acp`).
- Registry entries may declare `harness.acp_args` — the argv that enters ACP stdio mode (default `["acp"]`; Antigravity uses `["--uid="]`) — and all config-writing paths now honor it instead of hardcoding `["acp"]`.
- Cursor CLI support is removed; see breaking changes.

## Session slash commands

- ACP `available_commands_update` notifications now maintain a stored per-session slash-command projection (`name`, `description`, input hint; the latest advertisement wins, including an empty list). No derived event is emitted; the verbatim `session.update` row remains the source of truth.
- New routes (session tier, also on the local socket): `GET /v1/sessions/{id}/commands` returns `{ available_commands, updated_at }`, and `POST /v1/sessions/{id}/commands` takes `{ "command": "name", "args": "optional string" }` (a leading `/` is stripped), submits the composed `/name args` text through the normal prompt pipeline, and returns the prompt-submit shape plus an advisory `advertised` flag. Submission is never blocked on the stored list — it can be stale, and agents accept commands they never advertised. The session snapshot gains a matching `available_commands` field.
- Matching CLI surface: `acps sessions commands list <session-id>` and `acps sessions commands run <session-id> <command> [args...]`, which polls like `sessions prompt`; a command absent from the advertised list prints a warning but is still submitted.

## Providers, models, and endpoint overrides

- **Managed-state endpoint overrides**: credential apply accepts an optional `base_url` for the selected provider (https, or http to loopback only), routed into the agent's native config per-harness (opencode `options.baseURL`, pi `models.json`, codex `base_url`, Claude Code `ANTHROPIC_BASE_URL`) for agents declaring `set_provider_base_url` — now opencode, codex, pi, claude-code, and hermes. At most one provider may carry an override at a time; provider model-catalog fetches follow the override (`{base_url}/models`), and the catalog cache for both providers is invalidated on apply/clear. Every agent-change path — switch, Array target selection, init re-run, and fresh init — is guarded so a stored override can never be stranded on an agent that cannot route it.
- **Hermes endpoint and per-model wire shapes**: endpoint-carrying configurations (custom providers or override-routed mapped providers) now write a managed `providers.acps-managed` entry in `~/.hermes/config.yaml` carrying `base_url`, `key_env`, and `transport`, with `model.provider: custom:acps-managed`; `model.base_url` is never written anymore and is removed (existing files are migrated automatically on the next provision). The new `data/endpoints.toml` table records per-model wire shapes for OpenCode Zen/Go, resolved before the provider default; a Google-wire model under a managed endpoint is rejected at provision time. Hermes model switching remains config-based (`acps agent set --model` + restart), not live over ACP.
- **Provider catalog expansion**: Hermes provisioning coverage grows from openai/openrouter to over twenty documented API-key providers (anthropic, deepseek, google, xai, zai, huggingface, fireworks, alibaba, nvidia, ollama-cloud, and more), plus new hermes-only providers (`arcee`, `actual`, `commandcode`, `kilocode`, `meta-ai`) and aliases (`ai-gateway`, `fw`, `kimi`). The pi and opencode catalogs gain roughly twenty new providers (Ant Ling, Z.AI Coding Plan China, Qwen/Alibaba/StepFun/Tencent token plans, Cline Pass, Hetzner, LongCat, Modal, Poolside, Thinking Machines, and others). Fourteen providers gained verified `models_url` entries driving the live model catalog, and the init model picker's provider-catalog lane now covers Hermes (which advertises no models over its pre-1.0 ACP).
- **Claude Code provider profiles refreshed**: Z.AI/zhipuai defaults move to `glm-5.3[1m]` (haiku `glm-4.7`), MiniMax profiles to `MiniMax-M3[1m]`, Xiaomi profiles to `mimo-v2.5-pro[1m]`; DeepSeek gains a 768K auto-compact window; Microsoft Foundry accepts `ANTHROPIC_FOUNDRY_AUTH_TOKEN`; the Bedrock profile drops Pi-only env vars from the Claude Code lane.
- Codex provisioning rejects a double-qualified OpenRouter slug (`openrouter/<vendor>/<model>`) at init — OpenRouter answers an unknown slug with an empty turn instead of an error, so it previously failed invisibly at prompt time. Codex mode values are documented as adapter-advertised (`read-only`, `agent`, `agent-full-access`), not a fixed list.

## Switching, installs, and observability

- **Agent switch is journaled and convergent**: each switch records a fingerprinted journal (`agent-switch.json`) through `planned → committed → runtime_applied → completed`. Retrying an incomplete same-target switch resumes at the runtime re-apply (`provider_status: "resumed"`) when the candidate matches the journal, and a retry of a completed switch is a side-effect-free `no_op`. A bare same-target request is now accepted as already converged instead of failing "already configured". Conflicting requests return the new `409 agent.switch_conflict`; a corrupt journal returns `500 agent.switch_journal_corrupt`; session-target rename collisions return `409 session.target_rename_conflict`.
- **`GET /v1/installer/runs`** (session tier, also on the local socket) exposes live install progress from the `installer_runs` audit table: steps insert a `running` row at start (carrying server-computed `elapsed_seconds`) and finalize it in place, covering registry installs, escape-hatch shell installs, deps apply, and apt/native updates. Query params: `active=true`, `agent=<id>`, `limit` (default 100, max 1000). Reads use a short-lived second connection, so polling never blocks behind the daemon's shared state mutex.
- **`POST /v1/deps/apply` is non-blocking**: it no longer holds the shared state mutex for the whole run (a dedicated lock serializes back-to-back applies; audit rows write through a second connection), so unrelated HTTP requests answer during a multi-minute apply. `GET /v1/status` gains `deps_apply_in_flight` — an advisory that a restart should wait.
- **Install hardening**: registry shell installs may declare `timeout_secs` (whole-run budget overriding the 600s default, capped at 24h); install steps set `npm_config_python` from a bounded 5s probe so node-gyp skips version-manager shims; timed-out steps now persist the stdout/stderr drained up to the kill with an `[installer timed out after Ns]` marker instead of dropping it. The Hermes installer fetch fails fast (15s cap on a ~150KB script) with a GitHub-hosted fallback, and passes `--skip-setup --skip-computer-use --non-interactive` with explicit install dirs so root installs keep the managed `~/.local/bin/hermes` layout.
- `GET /v1/status` and `GET /v1/health/live` gain a `server.features` array (e.g. `network-provider-workload-env`, `agent-test-json`) as a capability signal, since nightly builds share the three-part base version. `acps agent test` supports `--format json` with a stable machine-readable document (`schema_version: 1`, `phase`, `code`, `fs_check`, `cleanup`), and its runs are now disposable — the test session is deleted when the agent advertises `session/delete` and no state-store row is written. Network-provider extensions gain `[extensions.<name>.workload_env]` for env vars injected into every workload in the provider's namespace.
- WebSocket operator disconnects (`POST /v1/ws/connections/disconnect`, `POST /v1/ws/sessions/disconnect`) accept an optional `reason` recorded as `operator_reason` on the disconnect event, and a dropped-notification bug (`notify_waiters` → `notify_one`) is fixed. `GET /v1/metrics/summary` always reports `api_connections.request_count` as a number.

## API contract and JSON Schema

- The typed `/v1` contract and `acps-config.toml` are published as JSON Schema (draft 2020-12) at `docs/specs/api/acps-schema.json`, generated from the Rust wire DTOs via schemars with `request`/`response`/`config` definition namespaces, plus a `acps-schema.meta.json` sidecar. Both are attached to every GitHub Release, so `releases/latest/download/acps-schema.json` is a stable URL. Drift and coverage tests run in the release gate — an un-regenerated DTO change fails the build and blocks tagging. WebSocket frames and envelope-bypassing handlers are deliberately out of scope.
- The API spec was tightened against the schema: previously undocumented routes and shapes are now pinned (init cancel routes, session `agent_sync`, prompt body shape, workspace upload fields, per-route log filters, metrics windows, deps apply outcomes, installer_runs enums), and config annotations now match loader validation (`restart` enum, array `targets` required, `timeout_secs` range 1–86400, `config_version` const 1).

## Internal

- Large modules were split into focused units (runtime subsystems, CLI and init flows, session routes, config schema) and large test suites reorganized; process capture, native-update probing, and provider-key resolution were deduplicated into shared helpers. The only behavior-visible changes are the `stack.update_binary_swap_failed` error typing noted above and a second process-group signal when an escalated deps-apply child survives the first kill.
